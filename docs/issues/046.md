# ISSUE-046: 客户端无信令心跳，半死连接导致接收方永远收不到文件提示

- **状态**: done
- **优先级**: P1
- **区域**: public/js/app.js, tests/smoke-ci.mjs

## 问题

服务端 room.ts 早已配 `setWebSocketAutoResponse(new WebSocketRequestResponsePair('ping','pong'))`，但客户端从不下发 ping，这条心跳是死配置。

后果是移动端（尤其 iOS Safari / 安卓后台标签被系统冻结数分钟后）底层 TCP 被静默杀死时，浏览器侧 `ws.readyState` 仍是 `OPEN`、`onclose` 不触发、UI 显示"已连接"。此时 `file-request` 信令是经服务端转发进这条半死管道的——发送方看着自己"发送成功/等待对方确认"，接收方却永远收不到任何提示，且不自愈。这正是"能发不能收、接收者永远接收不了"的非对称表现：发送方刚操作过连接是热的，接收方长时间挂着的那条早已半死。

（生产实测：同机双标签、跨 240s 空闲都无法复现，因为本地/桌面链路不会被中途掐断；问题特定于移动端后台冻结与跨运营商/代理静默断链场景。）

## 修复方案

- `startHeartbeat`：joined 后每 20s 发文本帧 `ping`；发出后 10s 内没等到 `pong` 判定连接已死，`handleDeadConnection` 摘除旧回调、强制断开并走标准重连（重连即重新 join、拿到新连接）。autoResponse 在 handleJoin 内配置，故心跳必须在收到 joined 之后启动，认证/等待期不 ping（否则收不到 pong 误判）。
- `onmessage` 在 `JSON.parse` 之前先拦截纯文本 `pong` 帧并清除超时，避免解析报错、也避免误入信令分支。
- `handleVisibilityChange`：页面恢复可见时立即补发一次 ping 探活，不空等下一个 20s 周期——移动端切回接收页的瞬间正是最需要探测的时刻。
- onclose / handleDeadConnection 统一 `stopHeartbeat`，杜绝定时器泄漏。
- smoke 增加 `ping→pong` 自动应答断言（独立连接复刻 app 时序）。注意 Node 风格 `ws.on('message')` 回调首参直接是 data 而非 event 对象。
