# ISSUE-033: 双端同时发起 offer 时协商判定失效，P2P 直连必然退回中继

- **状态**: done
- **优先级**: P0
- **区域**: public/js/webrtc.js, tests/webrtc-negotiation.test.mjs

## 问题

handleOffer 的 offerCollision 写成 `makingOffer || (signalingState !== 'stable' && signalingState !== 'have-local-offer')`，把 have-local-offer 排除在碰撞之外，不符合标准 Perfect Negotiation。

预热对双端都会触发（joined 的 peers.forEach 与 peer-joined 都走 addPeer → prewarmConnection），两端几乎同时 createOffer，双方都停在 have-local-offer 等应答。本端 offer 已发出、makingOffer 已复位时收到对方 offer，会被判成"无碰撞"，于是双方都 rollback 并互相应答对方的 offer：各自的 local(answer)/remote(offer) 不配对、DTLS 角色同为 active，握手必然冲突，P2P 直连失败退回中继。README 宣传的"P2P 直连"实际大量走中继，中继带宽成本也随之放大。

## 修复方案

恢复标准判定 `offerCollision = makingOffer || signalingState !== 'stable'`，让不礼貌的一方忽略收到的 offer、只有礼貌的一方回滚并应答。同时给 _attemptP2PConnectionSilent 补守卫：数据通道已存在（对方先握手、本端是被动应答方）时只等通道与密钥，不再 createDataChannel + createOffer，避免同一次握手里插入多余重协商并在两端各多出一条同名通道。

新增 tests/webrtc-negotiation.test.mjs，用 RTCPeerConnection 替身驱动 handleOffer，断言碰撞时恰好只有一方回滚；用旧实现跑该用例会失败。本机双端实测：修复前 connection-mode-badge 停在 data-mode="none"、安全码不出现，修复后 data-mode="p2p"。
